# EnvBisect — 처음 보는 사람을 위한 3분 발표

2026-09-19 · 개정 2 · 읽는 사람은 Node 내부 구조나 Daytona를 몰라도 된다.

## 발표가 끝났을 때 남아야 할 한 문장

**EnvBisect는 AI가 의심한 실패 조건을 여러 실행 환경에서 직접 시험해, 무엇을 바꾸었을 때 테스트가 다시 통과하는지 증거와 함께 돌려주는 실험형 디버거다.**

이야기의 순서는 **실패 뒤 남는 일 → 실행 증거의 필요 → 실험을 대신 수행하는 제품 → 정상/실패/회복 사례 → 개발자가 할 수 있는 다음 행동**이다.

## 0:00–0:30 · 기 — AI의 조언을 받은 다음에도 일이 남는다

화면에는 하나의 상황만 띄운다: **“런타임을 업데이트했더니, 어제 통과한 테스트가 실패했다.”**

> CI가 실패하면 개발자는 버전을 되돌리고 옵션을 바꾸며 재현 조건을 찾습니다. AI의 조언을 받아도, 실제 확인 작업은 남습니다.
>
> 한 SaaS 기업의 현장 연구에서는 모니터링과 실행 맥락 수집, 업무 개선을 함께 진행했습니다. 그 과정에서 재현 불가 버그는 33%에서 0%로, 평균 버그 처리 기간은 60일에서 15일로 줄었습니다.

화면 하단 주 출처: [Lentune SaaS 현장 연구, 출판사 초록](https://www.sciencedirect.com/science/article/pii/S0164121226002943). 작은 보조 출처로 [Google BRT 연구, 2025, §6.2](https://arxiv.org/html/2502.01821v2#S6.SS2)를 둔다. Google 수치는 말로 반복하지 않는다.

화면의 짧은 주석: **단일 기업의 모니터링·맥락 수집·업무 개선을 함께 진행한 결과. 환경 정보만의 효과나 EnvBisect 성과가 아님.** 처리 기간은 보고된 평균 closure time이다.

## 0:30–1:00 · 승 — EnvBisect가 그 확인 작업을 맡는다

아래 그림을 보여주며 말한다. **Daytona를 데모 뒤에 덧붙이지 않고, 제품이 작동하는 이유로 먼저 소개한다.**

```text
실패한 테스트 + 실행 조건
            ↓
EnvBisect의 AI: “어떤 조건을 바꿔 확인할까?”
            ↓
Daytona: 조건별 독립 실행 환경을 만들고 나란히 실행
            ↓
통과 / 실패 기록 → 다음 실험 선택 → 다시 실행
            ↓
검증된 실패 조건 + 통과한 변경 후보 + 재실행 기록
```

> EnvBisect는 이 확인 작업을 맡습니다. AI가 시험할 조건을 고르면, Daytona가 조건별로 독립된 임시 실행 환경을 만듭니다. 이전 버전, 실패 버전, 옵션을 바꾼 버전을 서로 섞지 않고 실행합니다.
>
> 결과를 보고 다음 실험을 고르고, 끝나면 환경을 정리합니다. 사용자가 매번 환경을 만들고 결과를 대조하는 과정을 제품 안에 넣은 것입니다.

## 1:00–1:45 · 전 — 무엇이 정상이고, 어떻게 실패했는가

**사례의 정체부터 밝힌다:** Node 공개 버그 #65601을 작게 재현해 사전 실행한 결과다. 고객사의 실제 CI 장애 기록은 아니다. CI 입력은 준비된 데모 데이터다.

화면은 아래 세 칸으로 시작한다. 먼저 “정상”을 설명한 뒤 버전 숫자를 읽는다.

| 정상이어야 하는 일 | 실제로 생긴 실패 | 바꾸어 확인한 결과 |
|---|---|---|
| 메모리의 바이트 데이터를 숫자 배열로 바라보는 작업이 **예외 없이 끝나야 한다** | 같은 코드·같은 8 B 입력이 Node **26.7.0에서는 통과**, **26.8.1에서는 RangeError** | 같은 실패 버전에서도 **배열 길이를 명시하면 통과**. 별도로 **26.9.0에서 기존 실패 케이스가 통과**한 기록도 확보 |

> 실제 공개 버그로 보겠습니다. 이 코드는 메모리 데이터를 숫자 배열로 바라보는 작업입니다. 정상이라면 예외 없이 끝나야 합니다.
>
> 같은 코드와 8바이트 입력이 이전 버전에서는 통과하는데, 26.8.1로 바꾸면 오류가 납니다. 이제 실패 버전은 그대로 두고 배열 길이를 명시해 실행하니 통과합니다. 메모리 할당 방식을 바꾼 실행도 통과합니다.
>
> 여기서 “새 버전은 전부 실패한다”는 설명보다 구체적인 조건을 얻습니다. 같은 버전에서도 실행 방식에 따라 결과가 갈립니다.

사전 기록과 현재 실행을 각각 `RECORDED` / `LIVE`로 표시한다. 26.9.0의 통과는 **기존 수정 버전의 동작을 확인한 것**이며 EnvBisect가 Node를 패치한 성과가 아니다.

## 1:45–2:10 · 전 — 앞선 결과가 다음 실험을 바꾼다

화면: **“할당 방식을 바꾸니 통과했다 → 입력 크기도 영향을 줄까?”** → 실제 AI 선택 → 새 실행 결과. 복잡한 변수명은 접어둔다.

> 이제 AI가 방금의 결과를 보고 입력 크기도 시험할지 결정합니다. 선택된 실험은 다시 Daytona에서 실행합니다.
>
> 이 장면이 핵심입니다. 준비된 결과표를 읽는 데서 끝나지 않고, 관측한 결과가 다음 실행으로 이어집니다. 최종적으로 실패한 조건과 통과한 변경, 그 실행 기록을 함께 남깁니다.

자동 선택과 새 실행이 실제로 연결됐을 때 사용하는 대본이다. 입력 크기 탐색의 사전 관측값 **32767 B FAIL / 32768 B PASS**는 보조 화면에 둔다. 이 숫자 자체를 이해해야 제품을 이해하는 구성으로 만들지 않는다.

## 2:10–2:40 · 결 — 개발자는 무엇을 얻는가

화면 제목: **“다음으로 무엇을 확인할지, 근거가 생겼다.”**

```text
확인된 실패: Node 26.8.1 + 테스트한 특정 배열 생성 조건
통과한 변경: 길이 명시 / 할당 방식 변경
별도 통과 기록: Node 26.9.0에서 같은 실패 케이스 통과
가져갈 것: 각 조건의 실행 명령·버전·결과
다음 행동: 후보를 실제 애플리케이션에 적용하고 전체 테스트 확인
```

> 개발자는 이제 어느 조건이 실패했고, 어떤 변경이 이 테스트를 통과시켰는지 확인할 수 있습니다. 수정 버전으로 올릴지, 코드의 사용 방식을 바꿀지 검토할 근거가 생깁니다.
>
> GitHub MCP와 실행 도구를 갖춘 agent도 같은 조사를 할 수 있습니다. EnvBisect는 그 실험 환경 준비, 비교, 다음 실험 선택과 기록을 반복 사용 가능한 기능으로 제공합니다. Daytona는 그때마다 필요한 실행 환경을 만들어 주는 기반입니다.

## 2:40–2:50 · 마지막 문장

> The LLM chooses the experiment. Daytona creates the worlds. Execution decides what's true.

2:50–3:00은 여유 시간이다. **사례의 성공 판정은 이 재현 테스트의 통과**이며 전체 앱의 정상화·안전한 수정까지 입증한 것은 아니다.

<details>
<summary>LLM + GitHub MCP와의 차이를 물으면</summary>

“그 agent가 같은 환경 대조·판정·증거 보존 흐름을 구현했다면 기능적으로 겹칩니다. 우리는 LLM의 추론 능력을 독점한다고 주장하지 않습니다. 조건별 실행 환경을 만들고, 한 조건씩 바꾸며 비교하고, 관측에 따라 다음 실험으로 이어지는 과정을 바로 쓸 수 있게 만듭니다.”

GitHub MCP는 저장소·Actions 기록 접근과 workflow 작업을 제공한다. “MCP는 읽기만 한다”거나 “agent는 실행하지 못한다”고 말하지 않는다. **GitHub 접근 기능을 연결하는 것과, 조건별 재현 실험을 설계·운영하는 것은 구분되는 작업**이다. [GitHub MCP 공식 설명](https://github.com/github/github-mcp-server)

Daytona의 가치는 구체적으로 세 가지다: **조건별 환경 분리, API로 생성·실행·삭제, 준비된 환경의 재사용**. snapshot은 반복 준비를 줄이는 선택 기능이다. 다른 sandbox·CI·컨테이너로도 구축할 수 있다. [Daytona 공식 문서](https://www.daytona.io/docs/en/snapshots/)

<summary>무대에서의 주장과 현재 구현 상태</summary>

- 준비 완료: Node·SciPy 재현 프로그램, Daytona runner, 사전 검증 기록.
- 당일 핵심: **실제 관측 → AI의 다음 실험 선택 → 새 실행**. 이 연결이 없으면 자동 실험 제품의 핵심은 미완성이다.
- 제품의 목표 입력은 실패한 CI 링크지만, 현재는 수동 RunBundle이다. “링크 하나면 모든 CI를 자동 복원한다”는 시연으로 보이지 않게 한다.
- 자동 코드 수정은 구현 범위가 아니다. 길이 명시·할당 방식 변경은 준비된 실험 옵션이고, 26.9.0은 이미 존재하는 수정 버전이다.
- 초기 Planner의 node domain은 26.7.0/26.8.1이다. 26.9.0 카드는 **별도의 사전 검증 기록**이며 현행 Planner가 자동으로 고른 결과가 아니다.
- snapshot 실측 4개 병렬 11.153→2.614초는 전체 loop 속도가 아니다.
- 자세한 수치·구현 계약은 [Handoff](EnvBisect_Handoff_Condensed.md)에 있다.

</details>

<details>
<summary>데모 지연·실패와 SciPy 대체 설명</summary>

전체 탐색을 무대에서 기다릴 필요는 없다. live 대조·실제 다음 선택을 보여주고 완료 기록으로 넘어갈 때 RECORDED라고 밝힌다. Planner가 연결되지 않으면 MANUAL, 증거가 부족하면 INCONCLUSIVE로 표시한다. 실제 선택이 다른 축이면 그 선택을 설명한다.

**SciPy 대체 사례도 같은 이야기 순서다.**

| 정상 | 실패 | 바꾼 뒤 확인 |
|---|---|---|
| 행렬에 역행렬을 곱하면 단위행렬에 가까워야 함 | SciPy 1.17.0의 같은 행렬에서 inv·solve-auto 오차 9.107408 | 같은 버전·행렬에서 solve-general 오차 5.47e-16, solve-sym 7.23e-16로 통과 |

“오류 메시지가 없어도 계산값이 틀릴 수 있습니다. 이 사례는 정답 조건을 검사하고, 같은 입력에서 계산 옵션을 바꿔 다시 검사했습니다.” Linux 실제 환경은 Python 3.14.4 / NumPy 2.3.5. 범주형 비교 사례이며 size 탐색 사례는 아니다.

</details>

<details>
<summary>연구·사전 실험 근거</summary>

오프닝의 SaaS 수치는 [출판사 초록](https://www.sciencedirect.com/science/article/pii/S0164121226002943)에서 확인한 Lentune 단일 기업의 결과다. 2024.7–2025.10의 5회 개선 주기에 모니터링·맥락 수집·교육·업무 개선이 함께 포함됐다. **“환경 정보 덕분에 60→15일”이라는 단일 원인 주장으로 바꾸지 않는다.** 출판사 권호는 2027.1 표기이며 확인일에 초록이 공개돼 있었고, 본문 표는 미확인이다.

Google 수치는 [2025 논문 §5.2.2·§6.2](https://arxiv.org/html/2502.01821v2#S6.SS2)의 23개 하위집합에서 13→17이다. oracle 테스트를 통과하는 후보 기준이며, 논문은 BRT 검증 방식상 효과의 상한으로 설명한다. EnvBisect의 시간 절감·수정률은 아직 측정하지 않았다.

Node 사례는 [공개 이슈 #65601](https://github.com/nodejs/node/issues/65601), [수정 PR #65605](https://github.com/nodejs/node/pull/65605), 우리 실행 결과는 [기존 Handoff §6](sources/EnvBisect_Handoff.original.md)를 근거로 한다. “정상”은 view 생성 중 예외가 없다는 oracle 의미다. 길이 명시는 임의 입력에서 원래 view와 동치인 범용 수정으로 입증한 것이 아니다. **Daytona Linux 검증은 26.8.1 기준**이다.

나머지 현업·환경·시장 근거는 [One Pager](EnvBisect_OnePager.md)와 Handoff 후반에서 확인한다.

</details>
