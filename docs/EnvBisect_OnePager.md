# EnvBisect — 실패 뒤의 확인 작업을 맡기는 디버거

2026-09-19 · 개정 2 · 처음 합류한 사람을 위한 한 장

## 기 · 왜 만들었나

런타임을 업데이트했더니 어제 통과한 CI가 실패했다. AI가 “버전 문제 같다”고 말해도, 개발자는 **이전 환경을 만들고 → 옵션을 바꾸고 → 재실행하고 → 결과를 비교**해야 한다. EnvBisect는 이 확인 작업을 맡기기 위해 출발했다.

실제 필요성도 확인했다: [Google 연구](https://arxiv.org/html/2502.01821v2#S6.SS2)는 23개 버그 하위집합에서 재현 테스트 제공 후 수정 후보 확보 **13→17개**를 보고했다. [SaaS 현장 연구](https://www.sciencedirect.com/science/article/pii/S0164121226002943)는 한 기업의 모니터링·업무 개선 과정에서 평균 closure **60→15일**을 보고했다. [Replay](https://www.replay.io/debugging)도 실행 기록을 사람·agent의 디버깅 입력으로 제공한다. 연구는 문제의 근거, 제품 사례는 시장 신호이며 **우리 성과·시장 규모 수치는 아니다**.

[2026년 개정 LLM 추론 엔진 버그 연구, Table 7](https://arxiv.org/html/2506.09713v2#S7)에서도 환경·설정 관련 버그의 평균 해결 기간은 각각 **37.8일·42.3일**이었다. 조사·대기·리뷰를 포함한 기간이며, 개발자가 실제 작업한 시간은 아니다. 이 수치는 문서용 근거로만 사용한다.

## 승 · 무엇을 대신 해주나

**EnvBisect는 AI가 고른 실패 조건을 여러 실행 환경에서 시험해, 무엇을 바꾸었을 때 테스트가 다시 통과하는지 증거와 함께 돌려준다.**

```text
실패한 테스트·환경 → AI가 다음 비교 선택
                         ↓
           Daytona가 조건별 독립 환경 생성·실행
                         ↓
                결과 비교 → 다음 실험 ↺
                         ↓
       검증된 실패 조건 + 통과한 변경 + 실행 기록
```

**LLM + GitHub MCP와의 관계:** GitHub 연결로 코드·CI 기록을 조사하고 workflow를 다룰 수 있다. EnvBisect는 그 위에서 **조건별 환경 준비·대조 실행·다음 실험 선택·증거 보존**을 하나의 기능으로 제공한다. 같은 흐름을 갖춘 agent와 기능은 겹친다. [GitHub 공식 설명](https://github.com/github/github-mcp-server)

**왜 Daytona인가:** “이 버전으로 다시 확인하자”는 AI의 선택을 **실제로 실행할 임시 환경**으로 바꾼다. 조건별 환경을 분리해 병렬 실행하고 API로 정리한다. 준비 snapshot으로 반복 설치도 줄일 수 있다. 이러한 환경 운영을 애플리케이션에 연결하는 부담을 낮춘다. 다른 인프라로도 구축 가능하다. [공식 문서](https://www.daytona.io/docs/en/snapshots/)

## 전 · 실제 사례로 이해하기

아래는 **실제 공개 버그를 작은 프로그램으로 재현해 사전 검증한 기록**이다. 가상의 결과나 자동 수정 성과가 아니다.

| | Demo A · Node #65601 | Demo B · SciPy #24359 |
|---|---|---|
| **정상** | 바이트 데이터를 숫자 배열로 바라보는 작업이 예외 없이 끝남 | 행렬 × 역행렬이 단위행렬에 가까움 |
| **실패** | 같은 코드·8 B 입력: 26.7.0 통과 → **26.8.1에서 예외** | 1.17.0 inv·solve-auto에서 오차 **9.107408** |
| **바꿔 확인** | 26.8.1 유지 + 길이 명시 시 통과. 별도로 **26.9.0의 기존 실패 케이스 통과** 확인 | 같은 버전·행렬 + solve-general·solve-sym 통과 |
| **배운 것** | 버전과 배열 생성 조건을 함께 봐야 한다 | 예외 유무만으로는 계산의 정답 여부를 알 수 없다 |

A의 후속 실험은 실패 조건을 고정하고 입력 크기를 바꾼다. 사전 기록의 **32767 B 실패 / 32768 B 통과**는 조건을 더 좁힌 보조 증거다. Linux A **105/105**, B **45/45**는 예상 PASS/FAIL과 일치한 관측 수다. [검증 원문 §6](sources/EnvBisect_Handoff.original.md)

## 결 · 무엇을 가져가며, 오늘 무엇을 만드나

**사용자가 가져갈 것:** 실패 조건, 통과한 변경 후보, 실행 명령·환경·결과. 이를 근거로 업그레이드나 코드 변경을 검토하고 전체 앱 테스트로 확인한다. 이 재현 테스트의 통과가 앱 전체의 수정 완료를 뜻하지는 않는다.

**준비된 것:** 재현 코드·판정 기준·Daytona runner. **오늘의 핵심:** 앞선 관측을 AI에 주고, 그 선택으로 새 실험을 실행하는 연결. CI 링크 자동 수집·자동 패치는 이후 과제다. 현재 입력은 수동 RunBundle이다.

**120분:** 0–10 접근 → 10–25 계약 → 25–45 실제 비교 → 45–70 AI 선택 → 70–95 새 실행·재검증 → 95–110 결과 출력 → 110–120 리허설.
**3분 발표:** 0–30 문제·근거 → 30–60 실험 방식·Daytona → 60–130 정상·실패·다음 실험 → 130–170 활용·차별점 → 10초 여유.

> The LLM chooses the experiment. Daytona creates the worlds. Execution decides what's true.
