We are now adding the presentation/product UI on top of the working EnvBisect terminal core.

Do NOT redesign the underlying experimental logic.

The UI is not a generic dashboard and not a chat interface.

Product thesis:
EnvBisect is an experimental diagnosis engine.
Its UI must visibly separate:
HYPOTHESIS → EXECUTION → EVIDENCE → NEXT EXPERIMENT → VERIFIED CONDITION.

Primary judging goals:
1. Real problem is immediately understandable.
2. Evidence changing the next experiment is the innovation.
3. Daytona worlds are visibly essential to execution.
4. The demo ends in a concrete evidence package.

Build ONE Experiment Workspace, not multiple SaaS pages.

Required UI flow:

1. Incident
- Prepared CI failure input
- Known good vs bad
- show only the initially observed Node runtime change

2. Verified baseline
- 26.7.0 PASS
- 26.8.1 FAIL
- reconstructed/executed status

3. Experiment 01
- Question: what conditions are required for the failure?
- four Daytona world cards
- each card visibly shows the intervention
- statuses transition RUNNING → PASS/FAIL

4. Evidence → Next Experiment
This is the most important visual moment.
Show the Round 1 observations.
Then show the planner-selected action:
SEARCH_BOUNDARY: size
and a short reason referencing actual observation IDs.

5. Boundary Explorer
- visualize deterministic probes over the numeric size range
- explicitly label this deterministic search, not AI guessing
- show the range narrowing from executed Daytona observations
- final observed adjacent transition

6. Evidence Package
- FAILURE CONDITION VERIFIED
- fixed conditions
- observed transition
- actual experiment/world counts
- evidence references
- Reproduce failing world / Copy reproduction command
- unfinished future actions should be visibly disabled, not fake-functional

Important UX concepts:
- experiment is the primary object, not logs/issues/chat
- use labels HYPOTHESIS / EXECUTING / EVIDENCE / VERIFIED
- every world should expose provenance:
  based-on world, changed factor, fixed factors, Daytona execution, cleanup
- show Daytona lifecycle subtly:
  creating isolated world → executing → observation captured → destroyed
- do not add auth, dashboard, settings, GitHub OAuth, chat, PR generation
- CLI/core truth remains the source of data
- never fabricate PASS/FAIL or known boundary values in UI
- LIVE / RECORDED / MANUAL states must remain explicit

Product copy:
EnvBisect
“Find the condition that makes your software fail.”

Supporting:
“AI designs the experiments. Daytona runs isolated worlds. Execution narrows the failure condition.”

The three demo moments we must optimize for:
A. Four Daytona worlds produce different outcomes.
B. Evidence visibly changes the next experiment.
C. A concrete adjacent FAIL/PASS condition is verified.

Before implementing visual polish, make these three moments work end-to-end.
